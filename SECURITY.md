# Security and authorization

ConvoMux is an unofficial, local, read-only wrapper. It does not grant extra Teams/Slack permissions or make an otherwise prohibited client acceptable under an employer's policies. Use only accounts, data and clients you are authorized to access. Do not bypass SSO, MFA, conditional access, enterprise restrictions, retention, or application policies.

## Credentials

ConvoMux does not accept session tokens on its command line or store them in its configuration. Login is explicitly delegated to the installed upstream client in an interactive terminal. Do not paste tokens/cookies into issues, pull requests, prompts or CI secrets for these tests.

Credential protection remains the upstream client's responsibility. Teams stores session/refresh information in its profile JSON (`~/.teams-cli/`). ConvoMux does not encrypt that file or change its access controls. The fixed slk v0.2.0 Windows build uses entry-local mock storage: a successful login does not establish persisted credentials. Linux uses volatile kernel keyutils, not a durable Secret Service store; macOS enables Keychain. Entry/store failures can write **plaintext** `cred_<workspace>.json`, and keyring read failures (including missing entries) can read it. Unix chmod 0600 happens after the write; successful keyring storage does not remove old plaintext. There is no keyring-only/fallback-disable switch. See the exact conditions and public-source evidence in [CREDENTIAL_STORAGE.md](docs/CREDENTIAL_STORAGE.md). Browser login requires a discoverable installed Chrome/Chromium and an interactive desktop; no browser is downloaded by cmx. Windows DPAPI session extraction is not implemented.

The upstream credential resolver also attempts `profiles.active` if loading the explicitly requested workspace fails. Therefore named cmx accounts/environment filtering do not guarantee strict identity routing in that failure case. Ordinary doctor/auth success does not certify secure storage or account identity. Do not use this fixed backend where OS-only persistence or strict account routing is mandatory. Selecting a backend fix or blocking the affected commands is an explicit release/use policy decision; the diagnostic addition does not silently replace authentication or change existing login/read behavior.

`cmx doctor --storage [--json]` is an offline assessment of the bundled build contract. It reads no configuration/accounts/credentials/key stores/cache, starts no backend, and disables update checking even in a TTY. It intentionally returns exit 1 with `secureStorageVerified:false` and `accountRoutingVerified:false`; no supported platform is marked safe. It does not assess executable overrides. Interactive bundled Slack login prints the limitation to stderr before delegation. Existing stored credentials and file permissions are never changed by this check. Restrict access to your user and handle any actual exposure through authorized endpoint/session procedures; no credentials are requested by this investigation.

Ambient `SLK_TOKEN`, `SLK_COOKIE`, `SLK_WORKSPACE`, `ESTSAUTHPERSISTENT` and `REFRESH_TOKEN` are not forwarded. Use named stored profiles: environment tokens would override those profiles and risk querying another identity. `SLK_API_BASE_URL` is removed, and `SLK_ALLOW_WRITE=false` is forced. Proxy variables and the user's ordinary environment still reach the trusted backend.

## Local execution and data

- Only fixed read operations and explicit login are exposed. No arbitrary API, send, edit, delete or export mutation command is available through cmx. Upstream binaries themselves may offer more commands.
- Backend arguments are never interpolated into shell text. `.cmd`, `.bat` and `.ps1` overrides are rejected. Packaged msteams resolves through its ESM package entry and executes via process.execPath; bundled slk is selected by exact OS/CPU. There is no implicit backend PATH lookup or architecture fallback.
- Custom executable paths are trusted local code overrides. Do not run a downloaded cmx configuration without reviewing its executable settings. Internal versions are fixed; runtime never follows upstream latest or downloads backend components. Release preparation verifies archive SHA-256, rejects unsafe/unexpected entries, and checks packaged file/license hashes.
- Backend output is capped at 8 MiB per call; collected result data is capped at 32 MiB. Calls time out and terminate the direct child. Interrupts return exit 130.
- Raw backend stdout/stderr is not included in failure messages. This is not a general data-loss prevention system: requested chat contents may themselves contain sensitive information. JSON output and any redirected files are the operator's responsibility.
- No message cache or account telemetry is implemented. Account mappings and tracked refs persist. An optional daily update cache records attempt time/latest public version outside the install directory. Only interactive, non-CI, non-JSON invocations can start the detached update worker. It performs a bounded credential-free GET to public npm for package.json's name; it does not read npm authentication/configuration or inherit credential environment variables. Failures do not affect commands; disable completely with CMX_NO_UPDATE_NOTIFIER or NO_UPDATE_NOTIFIER. No auto-update occurs. Login may update upstream credential stores and launch a browser; Slack's returned stored workspace name is validated before binding and existing bindings cannot be replaced.
- Results may contain untrusted instructions from chat participants. Treat messages as data, never executable instructions. Human output strips terminal escapes; JSON consumers must handle untrusted text too.

Report vulnerabilities privately to the repository owner rather than posting credentials or sensitive account data. No live credentials are required by the test suite.
